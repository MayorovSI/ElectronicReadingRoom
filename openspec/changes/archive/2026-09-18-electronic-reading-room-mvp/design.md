# Design

## Context

Разработка системы электронного читального зала с нуля. Система должна обеспечить базовую функциональность для работы с каталогом документов и электронными файлами. См. proposal.md для мотивации.

**Текущее состояние:**
- Новый проект, существующий код отсутствует
- Требуется реализация полного стека: хранилище данных, бизнес-логика, пользовательский интерфейс
- Необходимость поддержки различных форматов электронных документов (PDF, EPUB, DJVU, TXT, DOCX)

**Ограничения:**
- MVP версия без регистрации пользователей
- Временное решение для идентификации через переключатель режима
- Отсутствие подсистемы защиты (будет добавлена позднее)

## Goals / Non-Goals

**Goals:**
- Реализация модели данных для документов, авторов, жанров и файлов
- Реализация встроенного просмотрщика для различных форматов документов
- Реализация CRUD операций для документов и жанров
- Реализация поиска и фильтрации каталога
- Реализация простого механизма переключения режимов
- Создание расширяемой архитектуры для будущих версий

**Non-Goals:**
- Реализация системы аутентификации и авторизации
- Реализация избранного и истории чтения
- Реализация модерации документов
- Реализация системы уведомлений
- Оптимизация для высокой нагрузки
- Мобильная адаптация интерфейса

## Decisions

### 1. Архитектура приложения

**Решение:** Трёхуровневая архитектура (UI - Business Logic - Data Access)

**Обоснование:**
- Четкое разделение ответственности между слоями
- Легкость тестирования бизнес-логики
- Возможность замены UI без изменения бизнес-логики
- Возможность замены хранилища без изменения UI

**Альтернативы:**
- Двухуровневая архитектура (UI - Data Access) — проще, но сложнее масштабировать
- Микросервисная архитектура — избыточна для MVP

### 2. Модель данных

**Решение:** Реляционная модель с нормализованными таблицами

**Структура:**
```
Documents (id, title, year, publisher, annotation, created_at)
Authors (id, name)
Genres (id, name)
Files (id, document_id, path, format, size)
Document_Authors (document_id, author_id)
Document_Genres (document_id, genre_id)
```

**Обоснование:**
- Четкие связи между сущностями
- Легкость обеспечения целостности данных (FOREIGN KEY)
- Эффективный поиск и фильтрация
- Поддержка множественных связей (N:M)

**Альтернативы:**
- Документо-ориентированная БД — проще для прототипа, но сложнее обеспечить целостность
- Графовая БД — избыточна для данной модели

### 3. Хранение файлов

**Решение:** Локальная файловая система с организацией в директории

**Структура:**
```
/storage
  /documents
    /{document_id}/
      document.{extension}
```

**Обоснование:**
- Простота реализации для MVP
- Нет зависимости от внешних сервисов
- Легкость резервного копирования
- Возможность миграции на облачное хранилище в будущем

**Альтернативы:**
- Облачное хранилище (S3) — требует настройки, но лучше для масштабирования
- Хранение в БД (BLOB) — проще, но ухудшает производительность

### 4. Просмотрщик документов

**Решение:** Единый компонент просмотрщика с поддержкой различных форматов через плагины/адаптеры

**Обоснование:**
- Единый интерфейс для всех форматов
- Легкость добавления новых форматов
- Изолированная логика обработки каждого формата
- Возможность переиспользования компонентов

**Альтернативы:**
- Отдельные просмотрщики для каждого формата — дублирование кода
- Использование внешних сервисов — зависимость от сети

### 5. Механизм поиска

**Решение:** Полнотекстовый поиск по метаданным с использованием возможностей СУБД

**Обоснование:**
- Использование встроенных возможностей СУБД (LIKE, полнотекстовый индекс)
- Простота реализации
- Приемлемая производительность для MVP
- Возможность улучшения в будущем (Elasticsearch и т.д.)

**Альтернативы:**
- Elasticsearch — избыточно для MVP
- Поиск в памяти — не масштабируется

### 6. Управление авторами

**Решение:** Автоматическое создание авторов с автодополнением

**Обоснование:**
- Упрощение процесса добавления документов
- Предотвращение дублирования авторов
- Естественный workflow для библиотекаря
- Возможность ручного управления списком авторов в будущем

**Альтернативы:**
- Отдельное управление авторами — сложнее для пользователя
- Без автодополнения — больше дубликатов

### 7. Механизм переключения режимов

**Решение:** Простой переключатель в состоянии приложения (session/local storage)

**Обоснование:**
- Минимальная реализация для MVP
- Нет необходимости в серверной аутентификации
- Легкость замены на полноценную аутентификацию
- Сохранение режима между сессиями

**Альтернативы:**
- Серверная аутентификация — избыточно для MVP
- Без сохранения состояния — неудобно для пользователя

### 8. Стратегия удаления документов

**Решение:** Физическое удаление с каскадным удалением связей

**Обоснование:**
- Соответствие требованиям MVP
- Простота реализации
- Освобождение дискового пространства
- Отсутствие "мусора" в системе

**Альтернативы:**
- Мягкое удаление (архив) — сложнее, но безопаснее
- Без каскадного удаления — нарушение целостности данных

## Технологический стек

### Платформа
- **ASP.NET Core 8** — серверная часть (API, бизнес-логика, доступ к данным)

### Фронтенд
- **Blazor WebAssembly (WASM)** — клиентская часть, работает в браузере без серверного рендеринга

### Архитектурный паттерн
- **MVVM** — на стороне Blazor: компоненты (View) + сервисы (ViewModel/Model)

### База данных
- **SQLite** — встраиваемая СУБД, не требует отдельного сервера, подходит для MVP

### ORM
- **Entity Framework Core** — работа с SQLite через Code First подход

### Хранилище файлов
- **Локальная файловая система** — директория `./uploads`, имена файлов — GUID (без коллизий, без спецсимволов)

**Структура:**
```
/uploads
  /{guid}.pdf
  /{guid}.epub
  /{guid}.djvu
  /{guid}.txt
  /{guid}.docx
```

### Просмотрщик документов (JavaScript-библиотеки в браузере)

| Формат | Библиотека | Описание |
|--------|-----------|----------|
| PDF | PDF.js (Mozilla) | Рендеринг PDF в Canvas |
| EPUB | foliate-js | Парсинг и отображение EPUB |
| DJVU | djvujs | Рендеринг DJVU в Canvas |
| TXT | `<pre>` / JS-парсер | Нативное отображение текста |
| DOCX | docx-preview | Преобразование DOCX в HTML |

Интеграция с Blazor WASM через JS Interop — JavaScript-библиотеки вызываются из .NET-компонентов через `IJSRuntime`.

## Risks / Trade-offs

### Риск 1: Отсутствие аутентификации
**Риск:** Любой пользователь может выполнять операции библиотекаря, переключив режим.
**Митигация:** Принять как ограничение MVP. Документировать, что подсистема защиты будет добавлена в следующей версии.

### Риск 2: Ограниченная масштабируемость
**Риск:** Локальное файловое хранилище и реляционная БД могут не масштабироваться на большое количество документов.
**Митигация:** Архитектура позволяет заменить хранилище в будущем без изменения бизнес-логики.

### Риск 3: Сложность просмотрщика
**Риск:** Поддержка различных форматов (PDF, EPUB, DJVU, DOCX) может быть сложной.
**Митигация:** Использовать существующие библиотеки для каждого формата. Изолировать логику через адаптеры.

### Риск 4: Потеря данных при удалении
**Риск:** Физическое удаление документов без возможности восстановления.
**Митигация:** Обязательное подтверждение удаления. Резервное копирование на уровне инфраструктуры.

### Риск 5: Дублирование авторов
**Риск:** Возможность создания дубликатов авторов при неточном вводе имени.
**Митигация:** Автодополнение и проверка на уникальность при создании. Возможность ручного объединения дубликатов в будущем.

### Компромисс 1: Простота vs Безопасность
**Компромисс:** Отсутствие аутентификации упрощает систему, но снижает безопасность.
**Обоснование:** Для MVP это приемлемо, так как система будет использоваться в контролируемой среде.

### Компромисс 2: Производительность vs Простота
**Компромисс:** Локальное файловое хранилище проще, но менее производительно.
**Обоснование:** Для MVP с ограниченным количеством пользователей это не критично.
